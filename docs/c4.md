# `codeintel c4` — a LikeC4 architecture model from the code graph

`codeintel c4` turns an indexed repository into a [LikeC4](https://likec4.dev) model: a `.c4`
source file describing the repo's directories and files as nested elements, with the import graph
between them as relations.

```bash
codeintel c4 .
```

```
Wrote codeintel-c4/model.c4 — 61 elements at depth 4 (auto-fit: d1=2, d2=5, d3=46, d4=67), 212 relations
npx likec4 start codeintel-c4
```

## How this differs from `codeintel graph --html`

Both read the same index. They answer different questions, at different altitudes.

(Counts below are this repository measured on 2026-08-28; they move as the code and index do.)

| | `codeintel graph --html` | `codeintel c4` |
|---|---|---|
| Question | *what calls what* | *what depends on what* |
| Unit | individual functions | files and directories |
| Edges | function-to-function `CALLS` | file-level `IMPORTS` ∪ `CALLS`/`USAGE` |
| On this repo | 206 nodes, 220 edges | 61 elements, 212 relations |
| Output | one self-contained HTML file | `.c4` **source** |
| To view | double-click it — no dependencies | LikeC4 (Node ≥ 22.22.3, ~118 MB of npm) |
| Editable | no — regenerate it | yes, it is text you can commit and hand-edit |

Use `graph --html` to understand or debug a call path: it is function-level, needs nothing
installed, and handles the full graph. Use `c4` to document architecture or put a diagram in
review: it is committable, diffable, and a reviewer can correct it by editing text.

The split is deliberate. LikeC4 was evaluated as a *renderer* for codeintel and rejected on
measurement: a single view of 200 elements took 113 seconds to lay out, and 300 did not finish in
~8 minutes. codeintel's call graph is 1,054 functions and 2,900 `CALLS` edges, so LikeC4 cannot
draw what `graph --html` draws — which is why `c4` caps its views at 100 elements and rolls up to
files rather than functions.

## Viewing the model

`c4` writes DSL text; rendering is LikeC4's job. Cheapest first:

```bash
npx likec4 codegen mermaid -o diagram.mmd codeintel-c4   # zero install beyond npx; renders in GitHub
npx likec4 start codeintel-c4                            # interactive viewer
npx likec4 build -o ./site codeintel-c4                  # deployable static site
npx playwright install && npx likec4 export png codeintel-c4   # images need a headless browser
```

LikeC4 merges **every** `.c4` file it discovers under wherever it is started, so point it at the
model's own directory rather than the repo root. `c4` warns when it finds other `.c4` files
elsewhere in the repo for exactly this reason.

## Views: a landscape, plus a drill-down per area worth opening

A single `include root, root.**` view — everything, at every depth, in one diagram — is `include
*` with extra steps: on this repo that was 66 elements and 208 relations in one `autoLayout`,
unreadable regardless of how the includes were spelled. `c4` instead generates:

- **`view index`** — the landscape. Each top-level area and its **direct children only** (`root,
  root.*`, never `.**`). A nested area still renders as a compound box with its own children
  hidden, which is exactly what a landscape should look like. A pass-through directory that adds
  no information of its own (a bare, single-child wrapper with no branching — `src/` around a
  lone `codeintel/`, say) is collapsed through to the first area that actually branches.
- **A landscape root with more than `LANDSCAPE_CHILD_BUDGET` (12) direct children is elided**, not
  expanded. Depth-collapsing only helps a root with subdirectories to collapse THROUGH — a root
  that is itself flat and broad (many files, no further nesting) has no hierarchy for `.*` to
  exploit. An elided root's landscape line lists the root itself plus its child AREAS only; its
  flat leaf modules are left out of the landscape entirely and shown instead in that root's own
  drill-down view (next point) — the only place they appear.
- **One `view of <area> { include * }` per area worth opening** — at least two children, and small
  enough on its own that `include *` there does not reproduce the hairball one level down. Skipped
  for an ordinary landscape root (its children are already fully shown by the landscape's `root,
  root.*`), except an ELIDED root, which gets one for exactly the opposite reason: its children
  were left OUT of the landscape, and `view of <root>` is the only view that shows them. Capped at
  30 drill-down views total and skipped (with a stated count) for a repo branchy enough to blow
  past that.

Every view carries its own `title` and the same honest `description` the header states in prose.

**On a genuinely flat package** — many files, no subdirectories, which is this generator's own
`src/codeintel/` (41 direct children before elision) — elision plus a drill-down is a mitigation,
not a fix: directory containment has no hierarchy left to exploit once the drill-down still has to
show all 41 elements in one view. The actual fix is architectural LAYERS (grouping by role —
entry points, engines, providers — rather than by directory), specced in `docs/layers-design.md`
for a later session.

## What ends up in the model

**Elements** are directories (`area`) and files (`module`), rolled up to a depth chosen
automatically. Each carries `path`, `files`, `churn`, `fan_in`, `fan_out`, `internal_imports`
(references that stayed inside the element rather than being dropped), and `import_fan_in` (the
subset of `fan_in` confirmed by a real `IMPORTS` edge — see Hotspots below).

**An element id that would collide with a LikeC4 keyword** (`model`, `style`, `this`, `view`, …) is
escaped with a trailing `_` so the file still parses; the DISPLAYED title is always the real,
unescaped name. **A sanitisation collision** (`my-app/` and `my_app/` both sanitise to `my_app`)
is resolved by suffixing only the colliding path SEGMENT, not the whole id, so an uncontested
ancestor or descendant segment reads the same on both branches. **A same-directory, same-name file
across two languages** (`api/index.ts` + `api/index.js`) still merges into one element — undoing
that needs a second identity axis this model does not have — but every path is listed in that
element's `metadata`, not just one, `technology` reflects every language present, and the header
states how many elements this happened to.

**Relations** carry their provenance in the line style, because the two sources are not equally
trustworthy:

- `imports` (solid) — a real module-level `IMPORTS` edge contributed to it.
- `calls_usage` (dashed) — found **only** via the lower-precision `CALLS`/`USAGE` relation.

`IMPORTS` alone sees only module-level imports: on this repo, far fewer element-pair relations
than the union, with the majority found only via `CALLS`/`USAGE` — including the true `__main__ →
commands.*` and `gateway → providers.*` edges that this codebase's lazy `importlib` dispatch hides
from static analysis.

**Coverage is stated, not claimed.** The union still misses most of `__main__`'s `importlib`
dispatch table, and the graph backend sometimes fabricates an edge by matching a bare symbol name
against an unrelated same-named symbol. The generated header says so, the view description
repeats it where a diagram's reader will see it, and a test pins the known source→tests
fabrication so it cannot silently disappear.

## Hotspots: ranked on IMPORTS only, never the CALLS|USAGE union

An element with unusually high fan-in gets `#hotspot` plus a red fill — but "unusually high" is
ranked against `import_fan_in` (edges an `IMPORTS` relation actually confirmed), never the union
`fan_in` used for the descriptive metadata above.

Measured live on this repo: 54 of 60 `CALLS|USAGE` edges into `cache.py` were bare-symbol-name
matches — every `dict.get(...)` call anywhere in the codebase attributed to `ContentHashCache.get`.
Ranking a "this is an architectural hotspot" visual claim against that union would rank the
fabrication, not the architecture. A repo whose relations came only from `CALLS`/`USAGE` (no
`IMPORTS` edges at all) gets **no** hotspots flagged rather than falling back to that contaminated
signal.

The threshold is relative — this repo's own top decile among elements with at least one
`IMPORTS`-confirmed incoming reference, floored so a small or uniform repo is not misleadingly
declared to have one — not a fixed cutoff that tags a fixed fraction of every repo regardless of
its actual spread. The chosen threshold and how many elements it flagged are both in the header.

## Depth: chosen by fitting, never guessed

Assuming a `src/` source root produced a **completely empty model on 4 of 6** indexed
repositories — one has no `src/`, two are multi-root. So `c4` does not guess a scope. It excludes
noise directories, then picks the deepest roll-up depth whose element count still fits the
100-element view cap, and always reports the whole table:

```
// depth 4 chosen (auto-fit): d1=2 d2=5 d3=46 d4=67
```

so "why is this 67 boxes and not 600?" is answerable from the artifact alone — the table counts
every node that actually renders, including the bare containment areas a shared dot-prefix forces
into existence, not just the file/directory groups themselves. `--depth N` overrides it; over the
cap it warns and proceeds, because you asked.

`--scope PATH` (repeatable) narrows the model. It is an explicit override only, never detection:
a scope matching no indexed file is a hard error, not a signal to model something else.

Tests are excluded by default — they are not architecture and outnumber source in some repos.
`--include-tests` restores them.

`bin/` is **not** treated as noise. Every compiled artifact a `bin/` holds is already rejected by
the source-extension allowlist, which runs first — so excluding the directory removed nothing that
was not already excluded, while silently deleting the CLI entry points an npm package publishes via
`package.json#bin`. On one repo that cost three files and every relation in the model.

## Indexing

If the repo has no graph index, `c4` builds one and then generates, so a single command always
produces a model. It indexes the **graph only** — a `.c4` needs no embeddings, and on a 58-file
repo that is 6 seconds against 2m35s for a full index.

`--no-index` restores the strict behaviour: exit 1 with `project-not-indexed`. Use it in CI, where
a missing index should fail the step rather than be quietly repaired.

## Output isolation

LikeC4 merges every `.c4` under a directory, so a generated model gets its own (`codeintel-c4/` by
default) and `c4` is careful about what it will write over:

- A directory holding a `.c4` file **codeintel did not write** is refused — exit 1, nothing
  touched.
- A re-run overwrites the model it owns, tracked by a `.codeintel-c4.json` marker.
- A file the marker lists but this run did not produce is **removed**, so no orphan from an earlier
  run merges into the diagram.
- `--out` pointing at an existing file is refused.

## Styling

The palette is codeintel's own viewer tokens, verbatim — `#0c8ba6` (`--accent`), `#586472`
(`--muted`) and `#c0392b` (`--bad`, declared as `ci_bad`) from
`src/codeintel/viewer/graph_template.html` — via LikeC4 user-declared colours, so no config file is
needed and a generated diagram does not look like a different product from the call-graph viewer.
A hotspot's `#hotspot` tag and its per-instance fill override both resolve to `ci_bad` — one red,
not the tag's `#c0392b` next to an unrelated named theme colour on the element itself.

Per-channel control (separate fill/stroke/contrast) exists only in `likec4.config.json` under
`styles.theme.colors`; the equivalent DSL block form is a parse error in LikeC4 1.59.2. Note that
`styles.customCss` is present in LikeC4's shipped config schema but **rejected by its runtime
validator** in 1.59.2 (the latest release as of 2026-08-27), in both the JSON and `.js` config
forms — so custom stylesheets cannot currently be loaded that way.

## Validation

Nothing about this generator's output is trustworthy until something outside it parses the DSL —
so CI's `c4-validate` job runs `npx likec4@1.59.2 validate` against both this repo's own generated
model and a fixture repo whose file names are deliberately every reserved word LikeC4 1.59.2's
grammar rejects at identifier position (`model.ts`, `style.ts`, `this.ts`, …). It is
`continue-on-error` (like `lsp-contract`, for the same reason: `npx` reaching an external registry
is not fully within this project's control) so a registry outage does not block an unrelated
release, but it still shows as a red check — a claim about the DSL being parseable is worth having
only if something checks it, and a check that silently goes green when skipped is worse than none.

## Exit codes

| | |
|---|---|
| `0` | A model was written. |
| `1` | Nothing was written, and the reason is named: `engine-unavailable`, `project-not-indexed` (under `--no-index`), `project-not-indexed-standalone` (repo nested inside an already-indexed project), `no-source-files`, `scope-not-found`. |

Exit 1 on failure is deliberate: this command's job is to write a file, and exiting 0 having failed
to write it would report success to any CI step gating on `$?`.
