> **Status: historical record.** A point-in-time evaluation, kept because the reasoning and the
> measurements are worth having and correcting it would falsify the record. Written against codeintel
> **0.18.0**; the project is well past that. Where this disagrees with a reference doc, the reference
> doc wins.
>

> `codeintel c4` — see [c4.md](c4.md). The generator described in §4 as something built in a

## 0. Verdict

**Yes — but only in one direction, and only at one altitude.**

- **Use it as an *output format*.** codeintel should be able to emit a LikeC4 model
  (`codeintel c4` / `codeintel graph --format likec4`) from the graph engine's **Folder / File /
  Module + IMPORTS + HTTP_CALLS** slice. This is pure Python text generation — **zero new runtime
  dependencies**, nothing to install, nothing that can fail at query time. I built it and verified
  the output through LikeC4's own validator, JSON export, Mermaid codegen and static site build
  (§4).
- **Do not adopt it as a *renderer*.** Replacing or augmenting the self-contained HTML viewer with
  LikeC4 costs Node ≥ 22.22.3, 61 npm packages and **118 MB** of `node_modules`, and it does not
  survive contact with codeintel's actual scale: a single view containing 200 elements took **113
  seconds**, and 300 did not finish in ~8 minutes (§5). codeintel's call graph is 1,054 functions
  and 2,900 CALLS edges.
- **Do not treat it as a competitor to `code.query`.** LikeC4 ships an 18-tool MCP server whose tool
  *names* look like codeintel's ops (`query-graph`, `query-incomers-graph`, `find-relationship-paths`).
  It answers them over a **hand-authored** model. LikeC4 contains no source-code analyser of any
  kind — no tree-sitter, no Babel, no TypeScript compiler API; its only parser is the Langium grammar
  for its own `.c4` files (§2). The two tools do not answer the same question, and neither can
  produce the other's answer.

The one-line framing: **codeintel knows what the code *is*; LikeC4 knows how to draw what someone
*says* it is. The valuable seam is codeintel writing the thing LikeC4 draws.**

## 1. What LikeC4 actually is

### 1.1 Shape

An architecture-as-code DSL (inspired by the C4 model and Structurizr DSL) plus a toolchain that
turns it into diagrams. A TypeScript pnpm monorepo of 19 packages: `core` (typed model + view
computation), `language-server` (Langium grammar + LSP), `layouts` (Graphviz), `generators` (export
adapters), `diagram`/`react` (rendering), `likec4` (the CLI that composes them), `vscode`, and `mcp`.

| Fact | Value | Source |
|---|---|---|
| Licence | MIT, © 2023–2026 Denis Davydkov | `LICENSE` |
| Latest release | `1.59.2`, 2026-07-22 | `CHANGELOG.md` |
| Repo HEAD read | `84ff665`, 2026-08-11 | local clone |
| Runtime floor | **Node `>=22.22.3`** | `packages/likec4/package.json#engines` |
| Published size | 8.9 MB unpacked (`likec4` alone) | `npm view likec4 dist.unpackedSize` |
| Installed size | **118 MB, 61 packages, 17 s** | measured (§8) |
| Layout engine | Graphviz **via WASM** (`@hpcc-js/wasm-graphviz`) — no system `dot` needed | `packages/layouts/package.json` |
| Python support | **none** — zero Python anywhere in the repo | `grep -ril python packages/` → ∅ |

The Node floor is worth noting precisely: this container has Node `22.22.2` and is *one patch
version short*. It installs anyway (`engines` is advisory), but a project that pins that tightly
will keep moving.

### 1.2 The DSL is trivially generatable

Three blocks — `specification` (element kinds, tags, relationship kinds), `model` (nested elements
and `->` relations), `views`. It is line-oriented, brace-delimited, and has no forward-declaration
rules. LikeC4 generates it itself: `packages/generators/src/likec4/generate-likec4.ts` turns
structured data into DSL text, and its snapshot tests show the exact output shape. Emitting it from
Python is string formatting, not compilation.

### 1.3 Programmatic surface — and its one hard limit

From LikeC4's own docs (`apps/docs/.../tooling/model-api.mdx`):

> API allows to query and traverse the model from DSL, but **not modify or create a new one**.

`LikeC4.fromWorkspace(dir)` and `LikeC4.fromSource(string)` are the two entry points — both take
**DSL text**. Release `1.59.0` added a writeback path (`Builder.fromParsed()`, `LikeC4.toBuilder()`,
`LikeC4.toDSL()`, Node-only `writeDSL()`), explicitly documented as a **lossy** round-trip:
comments, source positions and formatting are not preserved.

Consequence for us: **DSL text is the integration contract.** There is no supported "hand LikeC4 a
JSON model" path from outside TypeScript, and the one that exists (`LikeC4Model.fromDump`) is a
`@likec4/core` API, not a CLI.

### 1.4 Health (second-hand)

GitHub project page, read 2026-08-26: **5.5k stars · 373 forks · 152 open issues · 27 watchers**.
Active — releases through 2026-07, commits into 2026-08, multiple recurring outside contributors in
the changelog, an NVIDIA copyright line in `packages/mcp`, community integrations, Discord, and
OpenCollective/GitHub Sponsors funding. Treat the digits as order-of-magnitude; the shape (healthy,
maintained, single-lead) is solid.

### 1.5 Precedent: this exact integration already exists for other stacks

- **[AspireC4](https://github.com/kjldev/aspirec4)** — auto-generates LikeC4 diagrams from the .NET
  Aspire resource graph. Community-maintained. **This is structurally the same integration this
  document proposes**, with Aspire's resource graph where codeintel's code graph would be.
- **[Erode](https://erode.dev)** — AI architecture-drift detection: compares code changes against a
  LikeC4 model. The nearest adjacent product to "codeintel + LikeC4", and worth watching as both
  validation and competition.
- **[mkdocs-likec4](https://github.com/doubleSlashde/mkdocs-likec4)** — embedding into docs sites.

The generator-feeds-LikeC4 pattern is established and welcomed by the project. codeintel would not
be doing anything unusual.

## 2. The overlap question — it is smaller than the tool names suggest

`@likec4/mcp` registers **18 read-only tools**: `list-projects`, `read-project-summary`,
`search-element`, `read-element`, `read-deployment`, `read-view`, `find-relationships`,
`find-relationship-paths`, `query-graph`, `query-incomers-graph`, `query-outgoers-graph`,
`query-by-metadata`, `query-by-tags`, `query-by-tag-pattern`, `batch-read-elements`, `element-diff`,
`subgraph-summary`, `apply-semantic-layout`.

Read cold, that table looks like codeintel's:

| codeintel op | LikeC4 tool that "looks like" it | Actually the same? |
|---|---|---|
| `callers` | `query-incomers-graph` | **No** — incomers of a *declared* element, not call sites |
| `callees` | `query-outgoers-graph` | **No** — same |
| `chain` | `find-relationship-paths` | **No** — BFS over declared relations |
| `impact` | `query-graph` (`includeIndirect`) | **No** — blast radius of a *drawing* |
| `overview` | `read-project-summary` | **No** — summary of the model file |
| `search` | `search-element` | **No** — id/title/kind/tag match, not embeddings |

The distinction that collapses all six rows: **LikeC4's model is written by a human and can be
wrong.** Nothing in LikeC4 reads source. Confirmed by absence, not by assumption — no `tree-sitter`,
no `@babel/parser`, no `typescript.createSourceFile` in any of the 19 packages; the sole parser is
`packages/language-server/src/like-c4.langium` (1,256 lines) for `.c4`/`.likec4` files.

So LikeC4's MCP server answers *"what does our architecture document say?"* and codeintel's
`code.query` answers *"what does the code do?"*. A team can run both, and the interesting question —
**do they agree?** — is exactly what Erode has productised.

**Zero-effort option available today:** a user registers both MCP servers. No code change, no risk,
nothing for codeintel to maintain. Worth one line in the README either way.

## 3. The abstraction gap — the real constraint

codeintel's own index (`CODE_INTEL.md`, this repo):

| Node type | Count | | Edge type | Count |
|---|---|---|---|---|
| Section | 1,170 | | DEFINES | 4,430 |
| **Function** | **1,054** | | **CALLS** | **2,900** |
| Variable | 336 | | USAGE | 1,991 |
| Method | 302 | | TESTS | 1,163 |
| **File** | **239** | | **IMPORTS** | **237** |
| **Module** | **238** | | **CONTAINS_FILE** | **236** |
| Class | 94 | | **HTTP_CALLS** | **90** |
| **Folder** | **46** | | **CONTAINS_FOLDER** | **32** |
| **Route** | **26** | | INHERITS | 1 |

A C4 diagram is meant to hold roughly 10–30 boxes per view. A LikeC4 model of 1,054 functions is not
a diagram, it is a hairball — and §5 shows the toolchain agrees, forcefully.

**But the bolded rows are a C4 model already.** Folder/File/Module with CONTAINS_FOLDER /
CONTAINS_FILE is precisely LikeC4's nested-element containment; IMPORTS and HTTP_CALLS are precisely
its relationships; `Route` is an element kind. codeintel's graph provider exposes arbitrary Cypher
(`GraphProvider._query_rows`), so this slice is directly queryable — no new backend capability
needed.

The mapping that works:

| codeintel | LikeC4 |
|---|---|
| `Folder` + CONTAINS_FOLDER | nested element, kind `package` |
| `File` / `Module` + CONTAINS_FILE | nested element, kind `module` |
| `IMPORTS` | `-[imports]->` relationship |
| `HTTP_CALLS` | `-[http]->` relationship (the genuinely C4-shaped one) |
| `Route` | element kind `route` |
| complexity / fan-in / LOC / path | `metadata { ... }` + a `#hotspot` tag |
| `chain` output | a **dynamic view** (ordered steps — LikeC4's sequence-diagram form) |

The `chain` → dynamic view mapping is the sleeper. LikeC4 dynamic views are ordered, titled,
annotated step lists that render as sequence diagrams with `alt`/`loop`/`parallel` frames. codeintel's
`chain` op already returns ordered, risk-labelled hops. That is a one-to-one fit and nothing else in
the category produces it from real call data.

## 4. Feasibility — measured, not estimated

I wrote a generator (~120 lines of Python, no dependencies) that walks codeintel's own package,
builds the Folder/File containment tree plus the import graph — the same shape the graph backend
returns — and emits LikeC4 DSL. Then I ran the real toolchain over it.

**Generated:** 57 elements, 105 relationships, **17,758 bytes** of DSL.

```likec4
specification {
  element package { notation 'Package'  style { shape rectangle  opacity 15% } }
  element module  { notation 'Module'   style { shape rectangle } }
  relationship imports { line solid }
  tag hotspot
}

model {
  codeintel = package 'codeintel' {
    #hotspot
    technology 'Python'
    metadata { file 'src/codeintel/__init__.py'  loc '2'  fan_in '13' }

    providers = package 'providers' {
      graph = module 'graph' {
        technology 'Python'
        metadata { file 'src/codeintel/providers/graph.py'  loc '1639'  fan_in '7' }
      }
      ...
    }
  }

  codeintel.gateway -[imports]-> codeintel.cache 'imports'
  codeintel.gateway -[imports]-> codeintel.policy 'imports'
  codeintel.gateway -[imports]-> codeintel.providers.none 'imports'
  ...
}
```

Results against LikeC4 `1.59.2`:

| Step | Result | Time |
|---|---|---|
| `likec4 validate` | **✓ Valid** (1 file, 0 errors) | 0.70 s |
| `likec4 export json` | 78 KB model JSON | 0.70 s |
| `likec4 codegen mmd` | 3 Mermaid files | 0.69 s |
| `likec4 build -o dist` | **5.2 MB** static site (`likec4-views.js` = 2.28 MB) | 1.74 s |

It works. Two things bit on the first pass, and both are findings, not accidents:

**4.1 LikeC4 forbids a relationship between an element and its own ancestor.** First run: 21 errors,
13 of them `Invalid parent-child relationship`. Every one was a submodule importing its own package:

```
codeintel.server   -> codeintel
codeintel.doctor   -> codeintel
codeintel.commands.query -> codeintel
… 10 more
```

That is **11 % of this repo's import edges (13 of 118) that a LikeC4 model cannot express.** It is
not a bug in either tool — a C4 model has no way to say "the part depends on the whole", and a Python
package `__init__` re-export makes that relationship completely ordinary. A generator must drop them
and **say so in a comment in the generated file**, or the diagram silently claims something false.
Given this project's stance on `deadcode`, a silent 11 % omission is not acceptable; an annotated one
is.

**4.2 View authoring is the actual work, not model generation.** `include *` at the top level yields
a view containing exactly one box — `index.mmd` came out at 110 bytes. LikeC4's `*` means
*top-level elements*, and the useful views need scoped predicates (`view x of codeintel.providers`,
`include codeintel.providers.**`). Generating a *model* is mechanical; generating *views that are
worth looking at* is a design problem, and it is where the effort in this feature actually sits.

## 5. The scale ceiling — this is the decisive number

Same generator, retargeted at symbols: 456 functions, 1,082 call edges (same order as codeintel's
real 1,054 / 2,900).

| Model | View | Result |
|---|---|---|
| 456 elements / 1,082 relations, deep nesting | trivial (`include *`) | **1.9 s ✓** |
| 456 elements / 1,082 relations | one view containing all of them | **no result in > 10 min** |

So the parser and the model are fine — **view computation is the ceiling.** Isolated with synthetic
models, one view, varying size:

| Elements in one view | Relations | `likec4 validate` |
|---|---|---|
| 100 | 200 | **1.6 s** |
| 200 | 400 | **113 s** |
| 300 | 600 | **did not finish in ~8 min** |
| 456 (real symbols) | 1,082 | **did not finish in > 10 min** |

Roughly 70× for a 2× increase in view size. LikeC4 is not built for this and does not claim to be — a
C4 view is supposed to have tens of boxes. But it settles the renderer question outright:

> **LikeC4 cannot render codeintel's call graph.** codeintel's own viewer draws 220 call edges by
> default and handles it interactively in a 38 KB self-contained HTML file with no dependencies.
> That is not a thing to trade away.

The practical rule for any generator we ship: **keep any single view under ~100 elements.** The
module-level model (57) sits comfortably inside that; the symbol-level model never will.

## 6. Options, ranked

Judged against the four properties the README sells: *local-first · never throws · one process ·
degrades instead of breaking*.

### A. Emit LikeC4 DSL — `codeintel c4` (or `graph --format likec4`) — **recommended**

Query the Folder/File/Module + IMPORTS/HTTP_CALLS slice, write `.c4`. Pure Python.

- **Cost:** ~150–250 lines (a `c4.py` sibling to `grapher.py`, same data→renderer split), plus view
  templates and tests. No new dependency in `pyproject.toml`.
- **Risk:** none to the invariants. Same never-raise shape as `grapher.build_graph_payload` — engine
  missing → write a file that says so, exit 1 because the command's job is to write a file.
- **Value:** users who already run LikeC4 get a model generated from *what the code does* rather than
  what someone remembered; users who don't lose nothing. Puts codeintel next to AspireC4 in LikeC4's
  own docs, which is free distribution into an audience of 5.5k stars — and this project's own
  measured problem is discovery, not engineering ([§1.3 of the status eval](eval-2026-08-23-status-and-market.md)).
- **Caveats to build in:** drop-and-annotate parent→child edges (§4.1); cap views at ~100 elements
  (§5); emit `metadata { file … }` so every box links back to source.

### B. Chain the MCP servers — **do today, costs one line**

Document that `codeintel` and `@likec4/mcp` compose: codeintel answers what the code does, LikeC4
answers what the model says. No code.

### C. Consume `.c4` as an input — the interesting one, but not now

If a repo already has a LikeC4 model, codeintel could map symbols to architecture elements and answer
*"which service does this function belong to, and does the code agree with the model?"* That is drift
detection — genuinely novel on top of a real call graph, and the highest-ceiling idea here.

**Blocked on parsing.** The grammar is 1,256 lines of Langium; a Python parser is a real project with
a permanent version-skew liability, and the alternative (shelling out to `likec4 export json`) drags
Node ≥ 22.22.3 and 118 MB into a Python tool's request path. It also collides directly with Erode.
Park it; revisit only if someone asks.

### D. Replace or augment the HTML viewer with LikeC4 — **no**

Node ≥ 22.22.3, 61 packages, 118 MB `node_modules`, a Vite build in the release pipeline, a 2.28 MB
`likec4-views.js`, `playwright` in the dependency tree for PNG export — and §5 says it cannot draw
the graph anyway. Every one of those is a straight subtraction from "one process, no build step,
open it offline".

---

## 7. Recommendation

1. **Ship option A** as an opt-in command. It is small, it cannot break anything at query time, and
   it is the only integration that uses each tool for what it is actually good at.
2. **Do option B now** — one README paragraph, zero risk.
3. **Say no to D** explicitly, in the doc, with the §5 numbers. This project already documents things
   it deliberately did not ship; that is a reason to record the measurement, not to leave it implicit.
4. **Park C** until an external user asks for drift detection.

The strategic point underneath: codeintel's measured weakness is not capability, it is
[distribution](eval-2026-08-23-status-and-market.md#13-adoption) — zero stars, zero external issues,
every bug so far self-found. A generator that makes codeintel the thing that *feeds* a 5.5k-star tool
with an established community-integrations page is a cheaper path to a first outside user than
another release.

## 8. Reproducing this

```bash
# LikeC4 source, read at 84ff665
GIT_LFS_SKIP_SMUDGE=1 git clone --depth 1 https://github.com/likec4/likec4

# the toolchain, actually installed and run
mkdir poc && cd poc && npm init -y
npm i likec4 --engine-strict=false        # 61 packages, 118 MB, 17 s
npm view likec4 version dist.unpackedSize engines

# the generator: walk src/codeintel, build Folder/File containment + the import graph
# (the shape `codebase-memory-mcp` returns), emit LikeC4 DSL.  Then:
./node_modules/.bin/likec4 validate .
./node_modules/.bin/likec4 export json -o model.json .
./node_modules/.bin/likec4 codegen mmd --outdir mmd .
./node_modules/.bin/likec4 build -o dist .

# the scale ceiling: N elements in 20-element groups, 2N random relations,
# one view with `include m0.**, m1.**, …`, timed with `likec4 validate`.
```

Environment: Linux container, Node `22.22.2`, npm `10.9.7`, Python 3.11, `likec4@1.59.2`. The
> 10-minute figures are wall-clock timeouts, not completions — the run was killed, so the true cost
is unknown and only bounded from below.

**Not measured:** rendering quality/legibility of the generated views by eye (no browser session
here), `likec4 export png` (needs Playwright browsers), and behaviour on a repo with a real
`HTTP_CALLS`-heavy service topology — which is the case where option A is *most* valuable and where
this evaluation is weakest.
