Three engines, seven ops, two repos. `callers` is genuinely good. `deadcode` is wrong in

violates the tool's central contract outright.

## 1. The root cause behind most of these bugs

The contract is:

```
{ok, op, target, result, engine, cached, reason?}
```

`ok` is always true. That leaves exactly **two** expressible states:

- `result` is non-null → "here is the answer"
- `result` is null + `reason` → "I could not answer"

There is no way to express the third state that actually occurs constantly in practice:

> **"I ran, I produced output, and that output is incomplete — and I know it."**

Every headline bug below is that third state being flattened into state one. A cold language
server returns *zero* references and it renders as `## References (none)`. A graph fallback to
a parent index returns a *different repo's* architecture and it renders as
`## Architecture: Repo B`. An op that found nothing because it never looked renders as
`(none found)`.

The never-raise contract is right. The problem is that never-raise was implemented as
*never-qualify*. **A wrong answer and a right answer are byte-identical to the caller**, which
is the exact risk the design set out to avoid.

## 2. Critical

### B1 — LSP returns `References (none)` on a cold language server

**Severity: critical. Reproducible on demand.**

Fresh 2-file TypeScript repo, two queries seconds apart, no edits between them:

```
Ground truth (grep):
  src/consumer.ts:1  import { makeWidgetFactory } from './factory';
  src/consumer.ts:6      this.w = makeWidgetFactory();

Query 1 (cold):  ## References  (none)   reason=None  hint=None
Query 2 (warm):  ## References (2)       reason=None
                 - src/consumer.ts:0  (consumer)
                 - src/consumer.ts:5  (WidgetConsumer/constructor)
```

`reason` null, `hint` null. Nothing distinguishes the empty answer from a true one.

Hit for real on Repo A: `symbol createEmbeddingProvider` returned `References (none)` cold,
while `callers` on the *same symbol* correctly returned `EmbeddingService.constructor`.

**Why it is the worst bug here.** "Who references this?" is the question an agent asks before
deleting or changing something. The false answer is *always* the permissive one: nobody uses
it, go ahead. And it self-heals on retry, so it will never reproduce when investigated by hand.

**Recommendation.**
1. `symbol` must not return a reference *list* until the server reports index-ready. serena/
   solid-lsp expose workspace-load state; gate on it. If the gate is not reachable within the
   query budget, return `result: null, reason: "backend-warming"` with a retry hint — never an
   empty list.
2. Structurally separate the two halves of the answer. A definition can be resolvable while
   references are not. Emit `definition` and `references` as distinct fields, each with its own
   completeness marker, so a partial answer is representable.
3. Add a regression test that runs `symbol` as the **first** call in a fresh process against a
   fresh fixture repo and asserts the result is either complete or explicitly incomplete —
   never a silently empty list. (This is the class of bug that only appears on call #1, so the
   test must own process startup.)

## 3. High

### B2 — `impact` callees contaminated by local-variable name resolution

`impact write_board_mirror` (Repo B). Callers correct. Callees:

```
- board_mirror_path                                                      OK
- serialize_board                                                        OK
- studio.src.main.preload.write        (studio/src/main/preload/index.ts)      WRONG
- tests.comms_board.test_comms_consolidate.conn                               WRONG
- app.features.archive…RUNNER_STATE.project_root  (….archive/…/*.json)     WRONG
- tests.conftest.tmp_path                                                     WRONG
- src.orchestrator.metrics.MetricsCollector.snapshot                    WRONG
```

**5 of 7 wrong.** Verified by reading `board_mirror.py:118-159` — `write`, `conn`,
`project_root`, `tmp_path`, `snapshot` are all parameter/local names inside that function.
`f.write(payload)` resolved to a **TypeScript** function in an Electron preload. Two parameter
names resolved to a pytest fixture and to a **JSON file inside `.archive/`**.

Three compounding defects: unqualified-name resolution that ignores scope, resolution that
crosses language boundaries, and non-code files admitted as symbol nodes.

**Recommendation.**
1. Never resolve a callee from a bare identifier that is bound in the caller's local scope —
   parameters, assignments, comprehension targets, `with`/`except` bindings. The extractor has
   this information at parse time; use it as a suppression list before global lookup.
2. Constrain resolution to the symbol's own language unless there is an explicit FFI/IPC edge
   type. A Python function cannot call a TS function by accident.
3. Method calls on a local receiver (`f.write`) must be typed or dropped, never matched on the
   attribute name alone.
4. Data files (`.json`, `.yaml`, `.toml`) may be `File` nodes but must never be candidates for
   `CALLS`/`USAGE` targets.
5. Exclude `.archive/`, `**/snapshots/`, and dot-directories from extraction by default.

### B3 — `deadcode` false positives (Repo A: 4 of 5)

| Candidate | Truth |
|---|---|
| `vite.config.background.generateBundle` | Rollup plugin hook. Deleting it breaks the extension build. |
| `tool-selection.prompts.'left-sidebar'` | Live entry in `AREA_MAP: Record<string, fn>`, dispatched by the runtime `area: string` argument of `resolveAreaCoordinates`. |
| `tool-selection.prompts.'right-sidebar'` | Same. |
| `streamCleanup.predicate` | **Indefensible.** `predicate: () => true` inside the object literal passed to `startListening({...})` on the same expression. |
| `sessionSlice.resetSessionState` | TRUE POSITIVE — absent from the `sessionSlice.actions` destructure at :589-631, no other reference. |

The sidebar case is the most misleading. Sibling keys in the **same object literal**
(`header`, `footer`, `sidebar`, `main`, `content`) were *not* flagged. The "verified against
the source" name-scan spares keys whose names happen to occur elsewhere as ordinary English
words and condemns the hyphenated ones. The filter manufactures the impression that these two
are special when the only difference is a hyphen.

**Recommendation.**
1. An object-literal property that is syntactically an argument to a call expression is not a
   deletable symbol. Exclude the entire class — it is a structural test, not a heuristic.
2. When *any* sibling key of an object literal is referenced, or the literal is typed as
   `Record<string, T>` / `dict[str, T]`, treat every key as reachable-by-dispatch and suppress
   the whole literal.
3. Framework-hook suppression by config surface: rollup/vite plugin objects, RTK
   `createSlice.reducers`, decorated handlers, `[project.scripts]` / `entry_points`,
   `__all__`. A curated list beats a name scan.
4. Rank candidates by *confidence* and emit the reason each survived, so the caller can see
   which check cleared it.

### B4 — `deadcode` false negatives (Repo B: `(none found)` from 4,883 functions)

```
src/orchestrator/runner/comms_formatters.py
  _format_decision      :48   never imported, no dynamic dispatch, no __all__
  _format_context_line  :54   same
  _format_question      :79   same
```

Their siblings `_format_age` and `_confidence_label` **are** imported by `comms_context.py`.
These three are textbook dead code and the op is silent. (`_state_cli`, also unreferenced, is
correctly not flagged — it is a `[project.scripts]` entry point.)

Wrong in both directions on the one op whose output is an instruction to delete code.

**Recommendation.** Pull `deadcode` from the default op set until precision *and* recall are
measured against a labelled fixture corpus. Ship it behind a flag, renamed to
`unreferenced-candidates`, with per-candidate confidence and the suppression reasons above.
An op that invites deletion has to earn a much higher bar than "returned something".

### B5 — semantic `search` returns prose instead of code

Repo B, `"where does the FSM decide the next stage transition"` — all 10 hits markdown:
`tests/snapshots/*.claude.md` (generated fixtures), `src/appdata/core/skills/*.md`,
`agents/support/orchestrator.md`. **Zero Python.** The actual answer,
`src/orchestrator/fsm/engine_transitions.py:22 → def evaluate_transition_rules(...)`,
was absent.

Repo A: 6/10 documentation (`flowDiagram/*.md`, `REFACTORING_COMPLETION_REPORT.md`,
`.github/backend-instructions.md`, `strategy/session-continuity/IMPLEMENTATION_PLAN.md`).

Prose *about* code out-ranks code because prose is written in the language of the query. In a
repo carrying a large `.md` corpus this makes `search` useless for finding implementations.

**Recommendation.**
1. Separate the corpora. Index code and prose into distinct namespaces and default `search` to
   code, with `--include-docs` to widen. Mixing them into one cosine ranking cannot be tuned
   out — the embedding is doing exactly what it was asked.
2. Exclude generated/snapshot/archive trees from the semantic index
   (`tests/snapshots/`, `.archive/`, `**/__snapshots__/`).
3. Boost chunks that carry a declaration (`def`/`class`/`function`/`export`) for
   implementation-shaped queries.
4. Report the corpus mix in the envelope, so `10 doc hits / 0 code hits` is visible rather
   than inferred.

### B6 — repo-wide ops answer from a parent index with no scope note

The refusal works for subdirectory queries: from `Repo A/backend`, `overview` and
`deadcode` both correctly returned `result: null, reason: "project-not-indexed-standalone"`.

But with `Repo B.db` hidden, the query fell back to the parent
`Documents/project/` index (visible in the `Repo B.`-prefixed qualified names) and:

- `callers` **correctly** appended `> Scope: … is not indexed on its own — this answer comes
  from the indexed project that contains it…`
- `overview` returned **`## Architecture: Repo B` — 27,210 nodes — no scope note, no
  reason.**
- `deadcode` returned **`(none found)`** — no scope note, no reason.

Same conditions, same command, three different honesty levels.

> **CORRECTION (verified after the architecture review).** My diagnosis above was wrong; the
> observation was not. Re-running the experiment with `overview` as the **first** call after
> hiding the `.db` returns `reason: "project-not-indexed-standalone"` — it refuses correctly,
> and still refuses after a `callers` call. **The scope gate exists, is singular, and works:**
> one resolver (`_lookup_project`, graph.py:568), one call site (graph.py:1157), one policy set
> (`_ROOT_SCOPED_OPS`, graph.py:40 — which does contain `overview`, `deadcode`, `hotspots`),
> enforced once and unconditionally on the query path (graph.py:1185). Ops cannot disagree by
> re-derivation because there is nothing to re-derive. "Resolve scope once before dispatch" is
> already the design.
>
> What I actually witnessed was a *different* state: `resolution.is_ancestor` was **false**
> because the project was still registered, so the answer came from a rebuilt/re-registered
> index whose data no longer matched the file I had hidden (node counts differed — 27,210 vs
> 27,231, CALLS 8,796 vs 8,939 — which is a *rebuilt* index, not the parent's). Two real
> defects produced it, neither of them a missing scope gate:
>
> 1. **Resolution trusts a registry claim it never checks against the returned data.** Hiding
>    a `.db` does not deregister the project, so resolution legitimately returns `exact` while
>    the backend answers from elsewhere.
> 2. **`_op_overview` titles the answer with the caller's basename**, not the answering
>    project's: `name = _repo_display_name(root)` (graph.py:974). That line exists for a good
>    reason — keeping a flattened home path out of a committed `CODE_INTEL.md` — and its side
>    effect is that the presentation layer asserts a provenance the data layer never
>    established. It is what turned wrong numbers into *confidently mislabelled* numbers.
>
> Severity accordingly drops from **high** to **medium**, and the fix changes completely: not a
> dispatcher gate (that exists and would have passed this case), but a **provenance check on
> the returned data** plus headings built from provenance rather than from the caller's path.
> Much of the residual is a symptom of B11's real cause — see the correction there.

**Still true:** `Documents/project/` is itself an indexed graph project and every repo here is
a subdirectory of it, so the ancestor path is live and reachable in normal use.

**Still true and unfixed:** semantic and LSP have no notion of scope at all. `ScopeVerdict` is
a `GraphProvider` concept that was never lifted to the other two engines — see B7, which is the
part of this cluster that is genuinely unfixed.

## 4. Medium

### B7 — semantic never refuses on scope
From `Repo A/backend`, `search "embedding provider factory"` silently returned results
scoped to `backend/` only, all 10 from `backend/test/`, missing
`backend/src/services/embedding/providers/embedding-provider.factory.ts` sitting right there.
Semantic has no equivalent of `project-not-indexed-standalone` and silently indexes whatever
subtree it is pointed at. **Fix:** route semantic through the same scope resolver as B6.

### B8 — phantom node counts in `overview`
A directory containing exactly one file, `q.py`, containing exactly `def q(): pass`:

```
## Architecture: neverindexed
17 nodes, 16 edges
- Class: 5     (there are zero)
- Method: 5    (there are zero)
- Function: 3  (there is one)
```

And `callers q` on the same project returned `reason: "not-in-graph"` — the graph
simultaneously claims 3 functions exist and that `q` is not one of them. **Fix:** the counts
are almost certainly schema/seed rows leaking into a project-scoped aggregate; scope the count
query by project id and add a fixture asserting exact counts on a known 1-symbol repo.

### B9 — absolute home paths leak, in `result` as well as `hint`

```
hint:   "`~/Documents/project/Repo A/backend` is not
         indexed on its own … Index it standalone with: codeintel index /Users/shammai…"
result: "> Scope: `~/Documents/project/Repo B` is not indexed …"
```

`codeintel status` additionally prints the flattened-path project id verbatim:
`resolved project 'Users-<user>-Documents-project-codeintel'` — the same form used
for every filename in `~/.cache/codebase-memory-mcp/`.

**Fix:** one `redact_path()` at the envelope boundary, applied to `result`, `hint` and
`reason` alike — render repo-relative, or `~/…`, or a stable opaque project id. The leak is in
`result` because the scope note is built by an op rather than by the envelope layer; centralise
it (same fix as B6).

### B10 — LSP line numbers are off by one, everywhere

| Reported | Actual |
|---|---|
| `board_mirror.py:117-158` | `def` at 118 |
| `board_mirror.py:193, 196, 214, 240` | calls at 194, 197, 215, 241 |
| `embedding-provider.factory.ts:5-20` | `def` at 6 |
| `alpha.py:0-2` | `def` at 1 |

`alpha.py:0` is the tell — not a valid line number. LSP is 0-based; the presentation layer is
1-based and never converts.

> **CORRECTION — this is worse than written: it affects two engines, not one.**
> `semantic.py:169` renders `f"{m['path']}:{m['line']} …"` where `m['line']` is `chunk_start`,
> 0-based by construction (`start0 = max(0, start - 1)`, indexer.py:406). My own transcript
> proves it and I read past it: semantic search returned `alpha.py:0` for a `def` on line 1,
> `alpha.py:4` for a `def` on line 5, and `q.py:0` for a one-line file. Fixing the LSP adapter
> alone ships half the bug.

**Fix:** not an adapter patch — a single `loc(file, line0)` helper that is the *only* thing in
the codebase permitted to format `file:line`, used by both renderers. Property-test that no
emitted line is ever `0` and that a known 0-based input renders as `n+1`.

### B11 — `reindexing: true` is stuck on
Every graph and semantic query in this entire evaluation returned `reindexing: true` with
*"a reindex is in progress — this answer reflects the index as of the last completed pass."*
Three consecutive queries 40 minutes after indexing finished, on a fully-indexed repo: still
true. On a 2-file scratch repo: still true. An always-on staleness flag is the same as no
staleness flag — I could not use it to detect the one genuinely stale answer I produced.

> **CORRECTION — the cause is not a bad derivation, and my fix was aimed at the wrong thing.**
> The flag is true because **the query itself started the reindex ten lines earlier**:
> `Gateway.query` calls `maybe_reindex` (gateway.py:262), which in a fresh process always passes
> the debounce (`_last_fired` is empty) and sets `_in_flight`; the same query then asks
> `reindex_pending` (gateway.py:272) and is told `true` — by itself. No mtime comparison is
> needed or would help.
>
> This is the third root cause I failed to name, and it is worth four bugs: **a one-shot CLI
> process runs the long-lived server's background machinery.** The pass is submitted to a
> *daemon* pool and killed mid-write when the process exits — every single query. That is B11,
> it is B17 (the walk restarts because the debounce state died with the last process), it is the
> most plausible source of B16's four `.corrupt` files, and it is very likely what re-registered
> the project underneath my B6 experiment.

**Fix:** `RunMode.ONESHOT | SERVER`. A process that cannot finish a reindex must not start one.
Then delete the field rather than derive it — it has been `true` for every answer this tool has
ever produced, which has trained every consumer to ignore it.

### B12 — `hotspots` only ranks `.tsx`
Both repos returned rankings that were **100% UI components** — every one of Repo A's top
25 is `frontend/**/*.tsx`, every one of Repo B's is `studio/**/*.tsx`. Meanwhile
`a large analysis module` (5,681 lines), `a large service module` (3,530),
`design_system.py` (1,267) and `terminal.py` (829) appear nowhere. Whatever computes
`cx`/`cog` is effectively only firing on JSX. It sends every refactoring conversation to the
frontend. **Fix:** verify the complexity visitor covers Python and non-JSX TypeScript; until
then, report per-language coverage in the result so the skew is visible.

### B13 — `reset --all --yes` does not clear graph indexes
It removed 3 semantic index files and left every graph DB in place — 40+ project DBs in
`~/.cache/codebase-memory-mcp`, dating to Aug 11, including an index of the **parent**
`Documents/project/` directory. The documented "start from a clean index" never happens on the
graph side. This is what made B6 exploitable. **Fix:** `--all` must mean all engines, or the
flag must be renamed and the limitation stated.

### B14 — `index` returns before the graph is ready, with a self-referential hint
`codeintel index <path>` returns after building only the semantic index; the graph lands
asynchronously. On a scratch repo, the first `callers` immediately after a *successful* index
returned `project-not-indexed` with the hint *"run: codeintel index &lt;the exact path just
indexed&gt;"*. A retry seconds later worked. **Fix:** either block until both engines are
queryable, or report per-engine index state and make the hint say "graph index still
building" rather than recommending a command that has already been run.

### B15 — archived and generated content is admitted as code
`app/features/.archive/…/RUNNER_STATE.json` appears as a graph symbol (B2);
`tests/snapshots/*.claude.md` dominates semantic search (B5). **Fix:** one shared ignore
policy consumed by *both* the graph extractor and the semantic indexer — today they clearly
have separate notions of what to skip.

## 6. What actually works

**`callers` is the strongest thing in the tool.** Cross-checked against grep on 5 symbols
across two languages — **zero missing call sites**:

- `createEmbeddingProvider` → 1 caller, exact
- `write_board_mirror` → 3 src functions + 2 test modules, exact
- `validate_adapter_model` → 3 src callers, exact, **including two lazy imports inside
  function bodies**
- `board_mirror_path`, `serialize_board`, `_format_age` → all complete

**Honest failure modes, where they fire.** `engine-unavailable` when uvx is off PATH;
`backend-error` with a real hint when serena will not respond; `project-not-indexed-standalone`
on subdirectory queries. No `Error executing tool` text or LSP init params ever reached a
`result`. The `--json` envelope is clean — progress chatter goes to stderr and does not
corrupt it.

**LSP references, once warm, are excellent.** `write_board_mirror` → 12 references, all real.
`AckLoopRunnerService` → 7 references matching grep. (It omits the 4 hits in
`__tests__/ack-loop-runner.spec.ts` — likely a tsconfig `include` boundary, arguably correct.)

**Vendored exclusion is correct.** `overview` reports 752 TS + 56 JS for Repo A (vs. 841 on
disk) and 718 TS + 394 Py for Repo B (exactly matching an independent count). No `node_modules`
or `.venv` leaked into any result.

**Nothing generated, vendored or minified appeared in `hotspots`.** Top 25 in both repos: all
hand-written source. That bug class is clean.

## 7. Recommended priority

*Reconciled with the architecture review. My original ordering is superseded — it ranked
`deadcode` above `search` and put a scope-gate rewrite at #2 that the code did not need.*

### Ship 1 — days. No contract change. Highest safety per line.

| # | Change | Kills |
|---|---|---|
| 1 | **Pull `deadcode` and `hotspots`** from the default op set, the tool description and `_MCP_INSTRUCTIONS` (which currently *recommends* both) | B3, B4, B12 — immediately, at zero risk |
| 2 | **`RunMode.ONESHOT`** — no background reindex in a process that cannot finish one; delete `reindexing` | B11, B17, most likely B16, and the churn under B6 |
| 3 | **CLI passes a budget; LSP cold budget → 30 s.** `commands/query.py:60-67` passes none, so LSP runs on `_DEFAULT_TIMEOUT_S = 5.0` against a cold first query measured here at **11.65 s** | over half of B1, for one argument |
| 4 | **`loc(file, line0)`** as the only formatter of `file:line`, in the LSP *and* semantic renderers | B10, both halves |
| 5 | **Stop titling `overview` with the caller's basename** (graph.py:974); stopgap `redact()` at the leaking hint/result sites | B9 partial, and B6's false attribution |

Item 3 is the finding I most regret missing: the mechanism behind the worst bug in the report is
a missing function argument.

### Ship 2 — 1–2 weeks. The structural change.

`Outcome`/`Answer` + a single assembly layer that owns completeness, scope, provenance,
coordinates and redaction — see §9. **B1 fully, B6, B7, B9 fully.** Tier-1 and Tier-2 tests land
*with* it, not after.

### Ship 3 — measurement-gated, in this order

B5 (semantic corpus split at query time) → our half of B2 (`callees` keyed on qualified name,
graph.py:872 currently matches the **unqualified** `a.name` and merges every same-named node) →
B14 index lifecycle → B13/B16 reset + `doctor` reporting `.corrupt` files → labelled deadcode
corpus → `hotspots` (`Function|Method`, graph.py:1115 queries `Function` only).

### Pull rather than fix

`deadcode` indefinitely; `hotspots` until a mixed-language fixture passes; `impact`'s **callees
half**, shipping `impact` as callers-plus-an-explicit-gap. The evidence supports this asymmetry
directly: callers was exact on 5 symbols across 2 languages with zero missing call sites, while
callees was 5/7 wrong on the one symbol tested.

**The highest-leverage change is structural**, and it is *not* the one I named first. Giving the
envelope a third state is necessary but would not, on its own, have fixed B1 — at the moment B1
occurs the process already *has* the failure and destroys it four conversions below the
envelope (`_call_tool` returns `None` on timeout, lsp.py:360 → `_loads(None)` → `_format_refs`
returns `[]`, lsp.py:441 → the default `"## References\n(none)"` at lsp.py:496 survives). The
machinery to report it correctly is already armed two frames away: `_extract_text` sets
`_last_backend_error` (lsp.py:384) and `build_result` turns exactly that into
`reason: "backend-error"` (lsp.py:311). `_op_symbol` simply never asks.

So the real defect is one level down: **there is no shared outcome type, so every internal seam
collapses five meanings into `None`** — never asked, timed out, backend errored, parsed to
nothing, genuinely empty. `graph.py` re-invented a fix for this three times in one file
(`_FAIL`/`_UNPARSABLE` at :426, `ProjectLookup` at :287, `_search_symbols`' deliberate
`None`-vs-`[]` at :799). `lsp.py` has none of them, which is precisely why the critical bug
lives in `lsp.py`. Make failures *values* internally and the envelope's third state falls out
as a derived property instead of a field someone has to remember to set.

## 8. Where the two analyses disagreed, and what settled it

This report was reviewed against the source by an independent architecture pass
([eval-2026-08-17-fix-architecture.md](eval-2026-08-17-fix-architecture.md)). Four of my
diagnoses did not survive it. The **evidence** in §2–§5 held in every case; the **mechanisms**
I inferred from black-box behaviour did not.

| Point | My diagnosis | After review | Settled by |
|---|---|---|---|
| **B6 scope** | ops each re-derive scope, so they disagree | Wrong. One resolver, one gate, all four repo-wide ops in it. Re-ran with `overview` **first**: it refuses correctly | Experiment + graph.py:40, :568, :1157, :1185 |
| **B1 cause** | language server not index-ready; gate on load state | Partly wrong. serena exposes no such state (lsp.py:164-172), and a gate would discard a correct definition. Real cause: **no budget passed** (query.py:60-67) → 5 s default vs an 11.65 s cold query | Source + my own timing |
| **B10 scope** | an LSP adapter off-by-one | Under-scoped. `semantic.py:169` has the same defect; my own transcript shows `alpha.py:0`, `q.py:0` and I read past it | indexer.py:406 + transcript |
| **B11 cause** | flag badly derived from mtime | Wrong. The query starts the reindex (gateway.py:262) then reports it (gateway.py:272) | Source |
| **B2 ownership** | five extractor fixes | Four of five are inside the external binary and cannot be done here. The half that *is* ours — `callees` keying on unqualified `a.name` (graph.py:872) — I missed | graph.py:870-879 |
| **B15** | graph and semantic have separate ignore policies | Wrong. `source_kind.py` already *is* the shared policy; it just cannot reach the external extractor | source_kind.py, indexer.py:353 |

Two of my judgements were upheld and one was strengthened: **pull `deadcode`** (the review
argues harder — don't schedule the fix at all, there is no evidence it can be made right), and
`hotspots` should sit behind the same gate rather than be filed as "skewed". The review also
found a defect I did not: `_op_hotspots` queries `label: "Function"` only (graph.py:1115),
excluding every `Method` node — which is what Python methods and TS class methods are. That is a
more likely explanation for the 100%-`.tsx` ranking than a missing complexity visitor.

**The methodological lesson.** Black-box adversarial testing found every one of these bugs and
misattributed five of them. Behaviour is evidence; mechanism is a hypothesis. Both passes were
necessary and neither was sufficient.

## 11. Follow-up round (2026-08-18)

Re-checking the fixes changed two conclusions and exposed one defect introduced by the fix itself.

**`hotspots` was fixed, not merely gated — reinstated.** It had been withdrawn on the grounds that
the fix was unverified. Running it proved otherwise: Repo B now ranks 11 `.py` / 12 `.tsx` / 2 `.ts`
with the four gnarliest Python functions on top (`_run_host` cx:58, `orchestrator._loop` cx:55,
`comms_post` cx:47, `_run_stage_via_terminal` cx:42), and Repo A ranks 18 `.ts` / 7 `.tsx` with
`UnifiedChatGateway.routeMessage` (cx:62, 658 lines) at #4 — a `Method` node, and therefore
invisible to the old `label: "Function"` query. `test_hotspots_ranks_across_languages` now gates it.
`deadcode` stays withdrawn.

**The provenance guard is unreachable, and was over-claimed.** Building the ancestor scenario
deliberately (a real git repo inside an indexed parent) shows the refusal at `graph.py:1185` fires
first and correctly returns `project-not-indexed-standalone`. `_answered_root_mismatch` only matters
in the hidden-`.db` case, which no test covers. It is belt-and-braces code with no exercise behind
it — worth keeping, not worth counting as a verified fix.

**`confidence` was shipped on one engine out of three — a defect introduced by the fix.** The MCP
instructions told callers to check a field that `graph` and `semantic` never set, and an ABSENT
field is ambiguous in exactly the way this field exists to remove: "complete" and "this engine does
not report" looked identical. That is the original bug, reintroduced one level up. All three engines
now stamp it through one shared `attach_confidence`, and a test enumerates the provider modules to
assert none hand-stamps it. Visible payoff: `impact` now returns
`confidence: partial, gaps: ["name-collisions-dropped"]` — B2's residual defect is disclosed rather
than silent.

Suite: 746 passed, coverage 85.07%.
